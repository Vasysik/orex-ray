# OrexRay 0.7.1 — план публичного выпуска

Основной сценарий должен целиком проходить на Android и Windows. Пользователь устанавливает или обновляет приложение, добавляет профиль, запускает VPN, видит ход подключения, проверяет прохождение трафика и отключается. Для 0.7.1 важны надёжность этого сценария, короткий старт без рекламы и обязательной регистрации, а также предсказуемые обновления.

## 1. Исправить запуск, отмену и восстановление

- **Операции.** Дать каждой попытке подключения идентификатор. Связать с ним старт, остановку, переключение профиля, ответы платформы, проверку маршрута и watchdog. После асинхронных границ проверять, актуальна ли попытка. Отменённая попытка освобождает только свои ресурсы. Поздние события от неё игнорируются.
- **Android.** Исправить воспроизведённую последовательность `stop → start` при отмене между первым событием `connecting` и отправкой команды сервису. Проверить отказ и отзыв разрешения, закрытие системного диалога, перезапуск процесса, Quick Settings, уход приложения в фон и смену сети.
- **Windows.** Проверить отмену во время валидации, запуска Xray и опроса TUN. Ограничить время ожидания `xray run -test` и сбор вывода. Заменить обязательную паузу 900 мс сигналом готовности с предельным таймаутом и наблюдением за завершением процесса. Опрос таблицы маршрутов оставить диагностикой. Проверить, что при ошибке или остановке процесс завершён, а исходные системные прокси-настройки восстановлены.
- **Состояние на экране.** Показывать фактические этапы платформы. Для Android это разрешение, создание интерфейса и старт ядра. Для Windows это подготовка конфига, старт ядра и применение выбранного режима. После запуска показывать «Проверяем маршрут». Зелёный статус появляется после успешной проверки трафика по активному маршруту. Для сбоя показывать понятную причину и следующее доступное действие.
- **Таймауты.** Развести ожидание разрешения, старт ядра, проверку маршрута и повторную проверку при смене сети. Ошибки конфигурации завершают попытку. Сетевые сбои получают ограниченные повторы. Один сбой проверочного URL не должен запускать бесконечные рестарты ядра.

Готово, когда автоматические проверки проходят для отмены до старта, во время разрешения, после запуска и во время проверки маршрута. Повторное подключение и смена профиля работают после отмены. При отказе и таймауте приложение возвращается в управляемое состояние. Выбранный режим подтверждён реальным трафиком.

## 2. Измерить задержку и убрать фризы

- Записать временные отметки нажатия кнопки, первого видимого состояния, старта Xray, готовности интерфейса или прокси и успешной проверки маршрута. Параллельно записать Flutter frame timings.
- Снять базовую линию на слабом физическом Android и Windows в profile-сборках. Раздельно прогнать холодный и повторный старт, одиночный профиль и крупный балансер, переключение профиля и активную статистику. Использовать одну рабочую тестовую конфигурацию и одинаковые условия сети для сравнения до и после. Для сценария отказа использовать контролируемый недоступный маршрут.
- По замерам решить, нужна ли сборка большого конфига в отдельном isolate, нужно ли сузить перерисовки главного экрана и выносить синхронные нативные вызовы. Перепроверить стекло, анимации и статистику по одному изменению за раз.

Предлагаемый бюджет для первого отклика — p95 до 150 мс в 30 запусках на каждом контрольном устройстве. До фиксации цели по времени подключения снять базовые значения отдельно по платформам и режимам. В итоговый отчёт включить p50/p95, долю кадров с превышением бюджета дисплея, таймауты и результат отмены. ВМ использовать для повторяемых функциональных проверок.

### Измерить энергопотребление Android

- На физическом телефоне сравнить VPN выключен, VPN подключён без нагрузки при погашенном экране и VPN передаёт воспроизводимый трафик. Повторить замеры с включёнными и выключенными скоростью и пингом в уведомлении. Зафиксировать устройство, длительность, заряд, тип сети, профиль и объём трафика. Сначала сравнить на одной сети, затем отдельно повторить на мобильной.
- В трассе сопоставить расход устройства с CPU обоих процессов, пробуждениями, сетевыми запросами и расходом радиомодуля. Исходные настройки при активном уведомлении — скорость раз в 5 секунд и пинг раз в 60 секунд, когда доступна проверка маршрута. Watchdog проверяет ядро раз в 5 секунд. Сравнить эти циклы, запросы Xray и таймеры Flutter при открытом UI. На поддерживаемом устройстве использовать Power Profiler. [Android Power Profiler](https://developer.android.com/studio/profile/power-profiler)
- Зафиксировать измеряемый расход простоя и фоновые операции за одинаковый интервал с несколькими повторами. Исправить воспроизводимую лишнюю активность, затем повторить тот же прогон. Проверить, что экономия сохраняет рабочее уведомление, своевременную проверку маршрута при открытии приложения и восстановление после смены сети.

## 3. Довести первый запуск и переводы

- Провести чистую установку без профилей. От главного экрана должен быть понятный путь к импорту ссылки, подписки, QR или JSON. Проверить понятную реакцию на пустой буфер, неподдерживаемую ссылку, недоступную подписку и отказ в разрешении VPN. При обновлении сохранить профили, подписки, темы, выбранный режим и язык.
- Базовые каталоги PL, ZH-Hans и AR уже покрывают навигацию, главный экран, ключевые состояния подключения и команды импорта. Английский исходник используется для пропусков. Попросить носителей проверить терминологию и заполнить пробелы первого сценария. Остальные строки можно добавлять отдельными PR после выпуска. [Работа с каталогами](localization.md)
- Для приложения перевести оставшиеся пользовательские сообщения Android на локализуемые причины с параметрами. Для уведомлений и Quick Settings использовать Android-ресурсы и согласовать их язык с настройкой приложения. Технические детали ядра оставить в диагностике.
- Проверить арабский RTL на телефоне и в окне Windows. Пройти навигацию, диалоги, поля ввода, адреса, порты, URL, цифры и копирование. Проверить польский при увеличенном шрифте и читаемость китайских иероглифов на обеих платформах. Прогнать смену языка и перезапуск на всех пяти языках.
- Проверить список приложений на телефоне с предустановленным YouTube. Приложение с включённым launcher-ярлыком видно в основном списке, даже если Android пометил пакет как системный. Системные компоненты без ярлыка скрываются отдельным фильтром, ранее выбранные пакеты видны. Проверить поиск, сохранение выбора после перезапуска и фактическое включение или исключение трафика после переподключения. [Флаги пакетов Android](https://developer.android.com/reference/android/content/pm/ApplicationInfo#FLAG_SYSTEM)
- Обновить EN/RU инструкции первой установки и release notes. Добавить короткий путь к сообщению об ошибке с версией, ОС, режимом, шагами и очищенным логом. По умолчанию диагностика остаётся локальной.

Готово, когда на чистой установке весь основной сценарий проходится на каждом заявленном языке. Допускается осознанный английский fallback для второстепенных экранов, включая продвинутые настройки и диагностику.

### Оценить запуск из уведомления и тематические иконки

- **Запуск Android VPN.** Рабочее уведомление удаляется при остановке сервиса. Если подтвердится спрос, попробовать отдельное уведомление «Подключить» с явным включением в настройках. Действие должно повторно использовать проверенный путь плитки Quick Settings, проверять актуальность сохранённого профиля и вызывать системный запрос разрешения при необходимости. Уведомление в состоянии покоя публикуется без постоянно работающего сервиса или опроса. Проверить холодный старт, повторные нажатия, отсутствие профиля, отозванное разрешение, запрет уведомлений и выключенный экран. При дублировании жизненного цикла или фоновой работе оставить плитку как основной быстрый запуск. [Ограничения фонового запуска Android](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start) · [Системное разрешение VPN](https://developer.android.com/develop/connectivity/vpn)
- **Иконки.** Для Android launcher рассмотреть adaptive icon с монохромным слоем. Цвет такого значка выбирает системная тема на поддерживаемом лаунчере. На Windows трей уже получает цвета из визуального состояния подключения. Проверить читаемость на светлой и тёмной теме. Иконки лаунчера и ярлыков, меняющиеся вместе с внутренним пресетом OrexRay, оставить отдельной задачей после проверки платформенного поведения. [Android adaptive icons](https://developer.android.com/develop/ui/compose/system/icon_design_adaptive)

## 4. Зафиксировать версию и упаковку

В GitHub Releases проверены 15 APK. У всех package ID `ru.orex.ray` и один сертификат подписи. Локальный APK с кодом 8015 отсутствует в этом наборе. [GitHub Releases](https://github.com/Vasysik/orex-ray/releases)

| Публичный тег | armeabi-v7a | arm64-v8a | x86_64 |
| --- | ---: | ---: | ---: |
| 0.6.4+4 | 1004 | 2004 | 4004 |
| 0.6.5+8 | 1008 | 2008 | 4008 |
| 0.6.7+10 | 1010 | 2010 | 4010 |
| 0.6.8+11 | 1011 | 2011 | 4011 |
| 0.7.0+13 | **1013** | **2013** | **4013** |

- Взять `0.7.1+16` как стартовый кандидат с учётом локальной сборки +15. Финальный номер назначить перед подписанием. Из чистого checkout собирать APK из логического номера `pubspec.yaml`. Проверять в готовых файлах package ID, ABI, `versionName`, фактический `versionCode`, постоянный сертификат Android и соответствие Windows версии и имени файла. Ожидаемые коды для +16 при действующей схеме — 1016, 2016 и 4016. Проверить до упаковки, что они строго выше публичного максимума для соответствующих ABI. Если APK с удвоенным смещением ABI раздавался вне GitHub, отдельно согласовать и протестировать путь обновления для его пользователей.
- Для релизной упаковки сверять входные артефакты с версией и коммитом. Проверять три APK, Windows setup и `SHA256SUMS.txt` после сборки. CI с временной подписью подтверждает компиляцию, выпуск подписывается постоянным ключом.
- Работать в коротких ветках от `dev`, затем влить проверенный кандидат через PR в `main`. Тег ставить на коммит, из которого собран опубликованный комплект. RC раздавать тестерам отдельно. Старый апдейтер принимает GitHub pre-release с обычным числовым тегом, поэтому публикация такого RC сделает его видимым текущим установкам. [Сборки](release-builds.md) · [Апдейтер](github-app-updates.md)

- Пропуск к публикации — зелёные analyze и тесты, обе сборки, подписанный комплект с проверенным обновлением поверх публичной версии и отсутствие открытых багов, которые ломают первый сценарий, отмену или восстановление сетевых настроек.
